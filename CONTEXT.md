# TripMate — Session Context

Read this FIRST, before grepping/exploring the codebase for a new task. It's a
living summary — update it (don't append forever; edit stale lines in place)
at the end of any session that changes architecture, fixes a real bug, or
learns something non-obvious. Full docs (`docs/ARCHITECTURE.md`, `docs/API.md`,
`docs/AGENT_PROMPTS.md`, `README.md`) are the source of truth for anything not
covered here — only go read them if this file doesn't answer the question.

## Stack (one line)

React 18 + Express 4 + MongoDB/Mongoose + Socket.io. Every AI call in this
codebase — Atlas chat, the trip-planning multi-agent pipeline, journal/
translation utilities — runs on Google Gemini (`gemini-3.6-flash` /
`gemini-3.5-flash-lite`, via Gemini's OpenAI-compatible endpoint using the
`openai` SDK as transport where a chat-completions shape is convenient).
OpenRouter, Groq, NVIDIA, and real OpenAI have all been fully removed
(2026-09-11) — a leaked NVIDIA key sitting in old git history was the trigger;
see "Known open issues" for the one action item that leaves (key rotation).
Deployed on Render: https://tripmate-ylt6.onrender.com

## Where things live

- `server/agent/agentLoop.ts` — Atlas chat loop + provider fallback
- `server/agent/tools/handlers/` — Atlas tool implementations (one per REST-equivalent action)
- `server/agent/multiAgent/MasterOrchestrator.ts` + `agents/` — separate non-chat pipeline (SuggestionAgent, ItineraryAgent, BudgetAgent, MapAgent, PackingAgent, JournalAgent, HeroImageAgent), tracked via `AgentJob`
- `server/controllers/` — REST handlers; most have an Atlas tool-handler twin doing the same mutation
- `shared/schema.ts` — single source of truth for Zod + Mongoose models
- `server/config.ts` — authoritative env var list
- `client/src/hooks/useUserLocation.ts` / `usePlaceSuggestions.ts` / `useTripDestinationCoords.ts` + `client/src/components/PlaceSearchDropdown.tsx` — shared place-search-with-suggestions stack (debounced, location-biased). Used by ActivityFormDialog, TripPlanner origin/destination, Emergency, OfflineMaps explore search, Weather (client-side distance sort, its dropdown predates this and has its own keyboard nav). Landing's hero destination search intentionally has no location bias (no "near me" for "where do you want to go").
- `client/src/lib/time.ts` — shared "HH:MM AM/PM" ⇄ minutes helpers + `nextAvailableTime()` (stacks a new activity after the day's last one instead of a fixed default time)
- `client/src/lib/queryClient.ts` — the ONLY HTTP client on the frontend (`apiRequest` for raw `Response`, `apiRequestJson<T>` for the common ok-check+parse+typed-error case, throwing `ApiRequestError` with a real `.status`). There is no axios anywhere in this codebase (removed 2026-10-01, see work log) — a second `client/src/lib/api/` axios layer existed in parallel for years duplicating this, now deleted.

## Non-obvious facts that cost real debugging time to learn

- **ID types are inconsistent by design**: `User._id` and most models use nanoid **strings**. `Trip._id` is a real Mongo **ObjectId**. A model with `userId: Schema.Types.ObjectId` when the actual value is a nanoid string silently CastErrors on every query — killed two whole features (Suggestions, Job History) before it was caught.
- **Trip collaborative writes are atomic-op-based, not `.save()`** (fixed 2026-08-31/09-01, commit `9144e4b`) — `expense.controller.ts`, `itinerary.controller.ts`, and their Atlas tool-handler twins use `$push`/`$pull`/`$set` with `arrayFilters` to avoid whole-document read-modify-write races. `modifyItineraryHandler.ts` is the one exception (needs the full itinerary read for its feasibility check) — it uses optimistic concurrency (compare-and-swap on `updatedAt`) instead.
- **Google Places Photo URLs must never embed `GOOGLE_API_KEY` client-side** — always go through `/api/v1/places/photo?ref=<photo_reference>` (server-side proxy, `redirect: "follow"` since Google 302s). This leaked 4 separate times across the session in different call sites before all were found — grep for `maps.googleapis.com/maps/api/place/photo` before shipping anything that touches Places.
- **Auth is cookie-primary**, not Bearer-primary — the SPA never sends an `Authorization` header; it's accepted as a fallback only. CSRF middleware skips the check when there's no auth cookie or when a Bearer header is present.
- **Avatars are base64-in-Mongo**, not disk-uploaded — Render's disk is ephemeral.
- **Maps use OpenTopoMap raster tiles** (`a.tile.opentopomap.org/{z}/{x}/{y}.png`), as of 2026-09-21 — the THIRD tile provider tried in one session, each abandoned for a different live-reproduced failure: OSM's `tile.openstreetmap.org` 403-blocks this app's request volume/pattern by design; MapTiler's key kept rendering an "Invalid key" placeholder even after a supposedly-corrected key was set on Render; CARTO's anonymous `basemaps.cartocdn.com` endpoint returns HTTP 200 with a real PNG even unauthenticated, but the PNG itself is watermarked "API KEY REQUIRED" across every tile — invisible from response headers/status codes alone, only caught via an actual screenshot. OpenTopoMap needs **no API key at all** and is confirmed CORS-open. Hardcoded to the `a.` subdomain specifically (not Leaflet's usual `{s}` round-robin across a/b/c) in `offlineTiles.ts`, `OfflineMaps.tsx`, and `TripMap.tsx` — all three must stay in sync on this exact URL, because `offlineTiles.ts`'s "Download for Offline" flow writes cached tiles under a concrete `a.` URL keyed by full request URL in the Cache Storage API; if the live components rotated subdomains, ~2/3 of tile requests after downloading a region would miss that cache and hit the network anyway, silently defeating the whole point of the download feature (caught in a code-review pass, fixed before it shipped). No separate dark tile style, so dark mode is a CSS invert-hue filter on the tile pane in both map components, not a layer swap — a real duplicate-tile-request bug was found and fixed here too: a dark-mode-toggle `useEffect` that swapped tile layers also fired once on initial mount (every `useEffect` does, regardless of its dependency array) and by then the map-init effect had already set `mapInstanceRef`/`tileLayerRef`, so its guard didn't skip it, firing a redundant second request for every tile already in flight (visible in DevTools as a 200 then a 400 for the same z/x/y). CSP (`server/middleware/security.middleware.ts`) allows `*.tile.opentopomap.org` (plus the now-unused `*.basemaps.cartocdn.com`/`api.maptiler.com`/`tile.openstreetmap.org`, kept so previously-cached tiles/CSP history under those hosts aren't dead weight to strip separately) in both `img-src` and `connect-src` — the service worker's tile-caching route re-fetches tile requests from inside the SW, which CSP checks against `connect-src` regardless of the original `<img>` request type. `sw.ts`'s cache-route matcher and `offlineTiles.ts`'s stored-region URL migration both cover all three abandoned providers so previously downloaded offline regions don't go blank after a provider switch. Offline regions can also be exported as a real `.zip`/image file to the device's Downloads folder (`exportRegionToImage`/`saveBlobToDevice` in `offlineTiles.ts`, "Save to Device" button in `OfflineMaps.tsx`) — separate from the Cache-Storage-based "Download" flow, which stays invisible to the OS file manager.
- **Navigation tab (`OfflineMaps.tsx`) has live turn-by-turn directions** (added 2026-09-21) — OSRM routing (`router.project-osrm.org`, `steps=true`) drives a `formatManeuver()` translator from OSRM's maneuver type/modifier into real instruction sentences. While "Tracking" is on, a throttled (8s) `useEffect` recomputes the route from the CURRENT GPS position on every position update — since this always routes from wherever the user currently is rather than tracking progress along the original path, it doubles as automatic off-route recalculation for free. The fetch is aborted via `AbortController` on effect cleanup so a stopped/unmounted navigation session can't apply a stale response afterward. Shows "You've arrived" within 30m of the destination.
- **QA/test accounts**: pattern is `@example.com` or `@tripmate.dev`, but real confirmed accounts also exist at other domains — always check with the user before bulk-deleting. `claude.code@tripmate.dev` is a persistent, intentional exception (not junk). Broad regex-scoped bulk deletes against prod trigger the safety classifier; itemized/exact-ID deletes don't.
- **Design system** is "Night Atlas / Passport & Visa Stamp" — dark-by-default via `:root` tokens in `client/src/index.css` (light is the `.light` override, not the reverse). The token palette has been expanded with canonical ink tokens (`--ink-blue`, `--customs-blue`, `--transit-green`, `--stamp-red`, `--warning-amber`) plus a full 8-way activity category register (`--ink-sightseeing`, `--ink-dining`, `--ink-lodging`, `--ink-transit`, `--ink-culture`, `--ink-nature`, `--ink-nightlife`, `--ink-shopping`) and their corresponding `--*-rgb` companions for Tailwind opacity modifiers. `--amber` is retained as a backwards-compatible alias to `--ink-blue`.
- **Never write `[var(--x)]/N` (Tailwind's arbitrary-value opacity modifier on a hex-valued CSS custom property) — it silently compiles to nothing.** Tailwind needs a space-separated RGB channel list to build `rgb(var(--x) / N%)`; a `var()` that resolves to `#rrggbb` can't be parsed that way and the whole utility class is dropped at build time (not even a broken rule — literally absent from the output CSS). Every ink token that's ever used with an opacity modifier has an `--x-rgb` companion in index.css (`--amber-rgb`, `--forest-rgb`, `--explorer-blue-rgb`, `--ios-red-rgb`, `--emerald-horizon-rgb`, and the new category `--ink-*-rgb` tokens) — use `[rgb(var(--x-rgb)/N%)]` instead. `[hsl(var(--x))]/N` (the shadcn-style HSL tokens: `--border`, `--muted-foreground`, `--card`, etc.) is unaffected and works fine as-is. This shipped broken across 8 files for an unknown span before a code-review agent caught it (2026-09-02, commit `bb94bf8`) — grep for `\]/\d` next to a bare `var(--` before assuming a hover/tint state is working.
- **Production auth endpoints (`/auth/signin`, `/auth/signup`) are rate-limited at 5 requests per 15-minute window**, separate from the general API limiter (100/15min) and far stricter than it looks from casual testing — a live-verification script that does more than ~4 signups/logins against production in a short span will self-lock for the rest of the window, and checking `ratelimit-remaining` itself counts as a request against the same window. Reuse one signed-in session (navigate/resize within it) across everything a live QA pass needs, instead of a fresh signup or login per page/viewport.
- **Playwright/Radix testing gotcha**: shadcn's `TabsTrigger` doesn't reliably expose a `[value="x"]` DOM attribute to query against — use `[role="tab"]` + a text match instead. And a raw `element.click()` via `page.evaluate()` does NOT activate a Radix Tabs/similar primitive (Radix listens for a real pointer-event sequence, not just a synthetic `'click'`) — use Playwright's own `.click({ force: true })` on a real element handle, not a JS-dispatched one.

## Non-obvious facts (cont.)

- **`Object.entries(req.body)` / `Object.assign(doc, req.body)` into a Mongo `$set` or a Mongoose document is a recurring vulnerability pattern in this codebase** — found 4 times (updateExpense, updateActivity, createPackingList, updatePackingList) before all were fixed with an explicit field allowlist. Grep for `Object.entries(` / `Object.assign(` near a `.save()` or `$set` before adding a new mutation route.
- **`validate.ts` now actually strips unknown body/query/param keys** (fixed 2026-09-01) — previously it ran `schema.parseAsync()` for its side effect of throwing on bad input but discarded the parsed result, so every Zod-validated route in the app accepted arbitrary extra keys through validation. If a controller ever seems to need a field the schema doesn't declare, add it to the schema — don't work around this middleware.
